# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Two things live here:

1. **Standalone Hebrew HTML files** — single-file apps opened directly in a browser (no build step).
2. **`food-logger/`** — a Node.js/Express PWA with a PostgreSQL backend and Claude AI nutritional analysis.

## food-logger

### Running

```bash
cd food-logger
npm run dev          # node --watch server.js (auto-restarts on change)
npm start            # node server.js (production)
```

### Environment variables (`.env` in `food-logger/`, see `.env.example`)

Validated once at startup by `src/config.js`; the process refuses to start (and lists every problem) if anything is invalid.

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string (required) |
| `JWT_SECRET` | Secret for signing session cookies (required, at least 32 characters) |
| `ANTHROPIC_API_KEY` | Claude API key for food analysis (required in production) |
| `ORIGIN` | The exact public URL of the app, e.g. `https://food.example.com` (scheme + host [+ port], no path; one trailing slash is tolerated). Used for the CSRF `Origin` check. Required in production; defaults to `http://localhost:3000` otherwise |
| `PORT` | Server port (defaults to `3000`) |
| `NODE_ENV` | `development` (default), `test` or `production`. Production turns on `Secure` cookies, HSTS and database TLS |
| `TRUST_PROXY` | Number of reverse-proxy hops to trust for the client IP (rate limiting). Default `1` in production, `0` otherwise |
| `DATABASE_CA` | Optional PEM CA certificate. When set, production database TLS is verified against it; when unset, verification is off and a warning is logged |
| `IMAGE_MODEL` | Model for the photo analysis. Default `claude-sonnet-5-5`; must match `^claude-[A-Za-z0-9._-]+$` (a set but blank value is an error: delete the variable to use the default). After changing it, check the server log for `not_found_error`: a mistyped id that fits the pattern makes every photo analysis return 502, and the cause appears only in the log. Back to Haiku without a code change: `IMAGE_MODEL=claude-haiku-4-5-20251001` (on Railway, in the service variables). The name-repair calls and the text analysis use `TEXT_MODEL`, not this. See AI below for the cost |
| `TEXT_MODEL` | Model for the text analysis (`POST /api/analyze-text`) and for the Hebrew name-repair calls of both analyses (`config.textModel`). Default `claude-haiku-4-5-20251001` (the exported `MODEL` constant); same validation as `IMAGE_MODEL` (must match `^claude-[A-Za-z0-9._-]+$`; a set but blank value is an error: delete the variable to use the default). To try Claude Haiku 5.5, on Railway set `TEXT_MODEL=claude-haiku-5-5` in the service variables; rollback: delete the variable. After changing it, check the server log for `not_found_error`: a mistyped id that fits the pattern makes every text analysis return 502, and the cause appears only in the log. The request rules per model family (Haiku 5: no temperature, effort low, `max_tokens` 4000) are in the AI paragraph below. The startup log line shows `textModel=<value>` |
| `IMAGE_EFFORT` | Latency/thinking setting of the photo analysis on Sonnet 5 (an id starting with `claude-sonnet-5`). One of `low` (default), `medium`, `high`, `off`; anything else, including a blank value, stops the startup with an error. Sonnet 5.5 spends many hidden thinking tokens before answering (about 8-17 s per photo); `low`, `medium` or `high` sends `thinking: { type: 'between_tools' }` with `output_config: { effort }`, which cuts that. `off` sends neither field (rollback: `IMAGE_EFFORT=off`, on Railway in the service variables). **Haiku 1-4, Opus and Fable never get these fields** (they reject them with a 400), whatever `IMAGE_EFFORT` says; `thinking: disabled`, `budget_tokens` and `temperature` are rejected by Sonnet 5 and are never sent. Text analysis is unaffected (its effort is the fixed constant `TEXT_EFFORT` = `low`). **Exception: `IMAGE_MODEL` set to a Haiku 5 or later id** (`claude-haiku-5-5`) does take `output_config: { effort }` from `IMAGE_EFFORT` (`low|medium|high`; `off` sends nothing), but never `thinking`. The startup log line shows `imageEffort=<value>` |
| `TEST_DATABASE_URL` | Database for the integration tests (see Tests). Defaults to `foodlogger_test` on the same server as `DATABASE_URL` |

### Architecture

- **`server.js`** — bootstrap only: loads `.env`, builds the config, pool, Anthropic client and icon, runs migrations, then `app.listen`.
- **`src/`** — the server:
  - `app.js` — `createApp({ config, pool, anthropic, icon, limits })` wires middleware and routers; never calls `listen` (tests import it).
  - `config.js` — env parsing and validation (`loadConfig`).
  - `db/` — `pool.js` (TLS policy and the UTC session pin: `createPinnedPool` builds the pool with `UtcClient`, which runs `SET TIME ZONE 'UTC'` inside `connect()`, fails closed if the SET fails, and keeps a temporary no-op `error` listener on the client during that round trip because pg-pool attaches its own only afterwards), `migrate.js` (runs `db/migrations/*.sql` in order, each in a transaction, under an advisory lock; applied versions are kept in `schema_migrations`) and the migrations (`001_baseline.sql`, `002_token_version.sql`, `003_food_photos.sql`). Tables: `users`, `food_logs`, `food_photos` (one JPEG thumbnail per meal, `ON DELETE CASCADE` from `food_logs`), `weight_logs`, `user_profiles`. Add a schema change as a new numbered migration, never by editing an applied one.
  - `middleware/` — `security.js` (CSP and other headers), `csrf.js`, `auth.js`, `validate.js` (zod), `rateLimit.js`, `errors.js` (error contract).
  - `routes/` — `auth`, `food`, `foodPhotos`, `weight`, `profile`, `stats`, `streak`, `analyze`.
  - `lib/` — `sessions.js` (cookie + JWT), `passwords.js` (bcrypt cost 12), `analysis.js`, `prompts.js` (the analysis prompts and JSON templates), `aiReply.js` (reply text and JSON extraction), `modelRules.js` (the pure per-model-family request rules, see AI below) and `anthropic.js` (AI), `hebrewName.js` (guard for food names, see "Hebrew copy and AI naming"), `image.js`, `dates.js`, `schemas.js`, `nutrition.js` (the sanity rules, see "Nutrition sanity rules"), `icon.js` (`buildIcon` draws the capybara-with-salad icon with `@napi-rs/canvas` at startup into `public/`: `apple-touch-icon.png` 180 px, `icon-192.png`, `icon-512.png` and the full-bleed `icon-maskable-512.png`; the generated PNGs are committed, the first one is also served by the `/apple-touch-icon.png` and `/favicon.ico` routes, `public/manifest.json` lists them and its `theme_color` / `background_color` are the leather colour `#22140c`).
- **`public/index.html`** — markup only (Hebrew RTL, the paper diary look, see "The diary design"); CSS in `public/css/` (`fonts`, `tokens`, `base`, `components`, `screens`), JS in `public/js/`, fonts self-hosted in `public/fonts/`.
- **AI** — `POST /api/analyze` (image) calls `config.imageModel` (`IMAGE_MODEL`, default `claude-sonnet-5-5`, chosen because it names meals far better than Haiku) and `POST /api/analyze-text` (free text) calls `config.textModel` (`TEXT_MODEL`, default `MODEL` = `claude-haiku-4-5-20251001`); both return a JSON nutritional estimate (the totals plus `items`, see "Analysis items"). The image prompt sizes portions by a scale-grounded method: it compares against reference objects visible in the photo (cutlery, a cup, a can, a card, a hand), writes them and the derived plate diameter in the model-only `scale_reference`, and asks for no volume (see "Portion estimation (image)"). The name-repair call of `hebrewName.js` (both analyses) also goes to `config.textModel` (`analyzeText` passes `model`, `analyzeImage` passes `repairModel`; both default to `MODEL`). The per-model request rules are pure functions in `src/lib/modelRules.js` (`temperatureFor`, `maxTokensFor` and `requestOptionsFor` are re-exported by `analysis.js`; also `textMaxTokensFor`, `repairMaxTokensFor`, `textRequestOptionsFor`), by family: **Haiku 1-4** (an id starting with `claude-haiku` that is not Haiku 5 or later, such as `claude-haiku-4-5-20251001`) sends exactly the request it always did (`temperature: 0`; `max_tokens` 1500 for the image, 1200 for the text analysis, 40 / 400 for the name repair; no extra fields; a test pins the Haiku 4.5 text request byte for byte); **Haiku 5 and later** (`^claude-haiku-(?:[5-9]|\d{2,})`) rejects a non-default temperature with a 400, so none is sent (nor `top_p`/`top_k`, a prefill or `thinking.budget_tokens`), adaptive thinking is on by default and its tokens count against `max_tokens`, so the caps are 4000 (name repair 2000, a named constant) and `output_config: { effort: 'low' }` keeps the thinking short (`TEXT_EFFORT`, fixed for the text route; the image route takes `IMAGE_EFFORT`); `thinking: { type: 'between_tools' }` is Sonnet 5.5 only and is never sent to Haiku, and there is no server-side fallback for a Haiku 5 refusal, so the code never sends `fallbacks` and a `refusal` is the same unusable reply as before (502 `AI_UNAVAILABLE`, not retried); **every other model** gets no temperature (newer models reject it) and `max_tokens: 6000`, because Sonnet can spend thinking tokens before its answer (many with `IMAGE_EFFORT=off`, far fewer at the default effort `low`) and they count against the cap. A Haiku 5 reply can start with `thinking` blocks: `aiReply.js` reads the first text block, and a reply with only thinking blocks is the existing no-text-block path (retried once, but not when `stop_reason` is `max_tokens`). The same text counts about 30% more tokens on Haiku 5. Sonnet costs about 4x more per image analysis than Haiku, and its thinking tokens (billed as output tokens) can push the real cost above that; the caps below bound it. Replies are read by `lib/aiReply.js`: the first text block (plus the text blocks right after it), then the JSON (whole text, an optional code fence stripped, else the first balanced `{…}` / `[…]` span that parses and is an acceptable answer: a non-empty items array, never the prompt's own JSON template, which `analysis.js` builds the prompts from); a reply without a text block or without parseable JSON is `502 AI_UNAVAILABLE`, logged with its block types and `stop_reason`, never its text. Such an unparseable reply is retried once by `withParseRetry` in `analysis.js` (both paths; never an API error, never a reply cut by `max_tokens`), so a retry doubles the cost of that one request while the limiters below still count requests, not calls. A `refusal` is not retried either. `requestOptionsFor(model, effort)` adds the Sonnet 5 low-latency fields (see `IMAGE_EFFORT`) and, for a Haiku 5 or later model, only `output_config.effort`; Opus and Fable never get them; `analyzeImage` also takes an evaluation-only `prompts: { system, user }` override that production never passes. The startup log line (`startupLine` in `config.js`) states both models and `imageEffort`. Rate limited to 20 requests/hour per **user**, plus a per-**IP** cap of 60 requests/hour shared by both endpoints (registration is open, so per-user alone would let a script mint accounts to multiply billed calls). Knobs: `limits.analyzePerHour`, `limits.analyzePerIpPerHour`.

### Meal thumbnails

Each meal can carry one small JPEG, stored in `food_photos` (table above) and served by `src/routes/foodPhotos.js`, mounted on `/api/food` before the food router. The browser creates the thumbnail; `public/js/photos.js` holds `photoSrc(id)`, the image URL.
- `PUT /api/food/:id/photo`: session cookie, the CSRF headers and a per-user limit of 200 stores per hour (`limits.photoPerHour`) and a per-IP limit of 300 per hour shared by all users (`limits.photoPerIpPerHour`, registration is open) apply. The raw body must be `Content-Type: image/jpeg`; it is checked in this order: the parser reads at most 130 KB (`express.raw`), the bytes must be a JPEG (magic `FF D8 FF`, via `detectImageType`) whose frame header, read by `parseJpegSize` in `src/lib/image.js` without decoding, says at most 640 px on each side, and the length must be at most 122 880 bytes (120 KB). Any other type, magic, size or an empty body: `400 VALIDATION` with `fields: { photo: 'INVALID' }`. A body over the parser limit or over 120 KB: `400 VALIDATION` without fields (the existing body-parser mapping of `errors.js`, which has no 413). The row is written by one `INSERT ... SELECT ... FROM food_logs WHERE id AND user_id ... ON CONFLICT DO UPDATE`, so a second PUT replaces the thumbnail, and a meal that is missing or belongs to someone else gives the same `404 NOT_FOUND` with the same body. Reply `{ ok: true }`.
- `GET /api/food/:id/photo`: session cookie; owner only (`404 NOT_FOUND` for a missing photo, a missing meal and another user's meal alike); `Content-Type: image/jpeg`, `Cache-Control: private, no-cache` with `Vary: Cookie` and a strong `ETag` (a sha1 of the bytes): the browser always revalidates, so a signed-out browser is never served the previous user's picture from its cache, and a replaced thumbnail is picked up. The `304` for a matching `If-None-Match` is produced only after auth and the ownership query, so another user or a request without a session gets the normal `404` / `401`, never a `304`. The CSP `img-src 'self'` already covers it.
- `GET /api/food` rows carry one extra field, `has_photo` (boolean, an `EXISTS` on `food_photos`); `POST` and `PUT` rows do not.

### Analysis items

Both analyses (`POST /api/analyze`, `/api/analyze-text`) reply with the old fields (`foodName`, `calories`, `protein_g`, `carbs_g`, `fat_g`, `fiber_g`) **plus `items: [{ name, calories }]`** (older clients ignore it), built by `replyItems` in `src/lib/analysis.js` from the items AFTER the sanity rules (so the calories are the checked ones): in model order, at most 8, the name through `cleanDishName` and cut to 40 characters (a name without a Hebrew letter becomes `פריט`), calories a rounded non-negative integer. **Never a weight or volume** (grams of components are never shown to the user and never editable). The totals are computed from all the model's items, not only the 8 returned; the names are never logged. The client draws them on the receipt (`receiptHtml` in `public/js/receipt.js`) at analysis time only; they are not stored. The receipt adds one `ועוד` row with the remainder calories (total minus the sum of the items) only when all 8 items arrived and the remainder is more than 4 kcal (the most that rounding 8 items can drift).

### Profile and target weight

`GET/PUT /api/profile` keep an allow-listed JSON in `user_profiles.profile_json` (unknown keys are stripped): `gender`, `birthDate`, `height`, `weight`, `activity`, `goalKg` (the weekly change in kg) and **`goalWeight`**, the target weight in kg: `0` or absent means unset, otherwise 20..400 stored with one decimal (a value is rounded, not rejected; garbage is `400 VALIDATION`). The schema is in `src/routes/profile.js` and uses `zeroOrRangedNumber` from `src/lib/schemas.js`; no migration. The browser reads it with `goalWeightOf(profile)` (`public/js/profile.js`) and prints kg with `formatKg` (`public/js/format.js`: `72.5`, `70`, `1,000.5`); the profile slip has the field `#mp-goal-weight`, the settings row shows it in `#settings-goalweight` ("לא הוגדר" when unset), and the weight screen shows `ק״ג · יעד N` with the dashed goal line only when it is set.

### Operating the image model

The image analysis defaults to Sonnet (`IMAGE_MODEL=claude-sonnet-5-5`), about 3-5x the cost per photo of Haiku. Set a monthly spend limit in the Anthropic Console. To roll back, set `IMAGE_MODEL=claude-haiku-4-5-20251001` (the Haiku request is unchanged); to keep Sonnet but drop the low-latency fields, set `IMAGE_EFFORT=off`. Since this version the default sends `thinking: {type: 'between_tools'}` with `output_config: {effort: 'low'}` to Sonnet 5 models (an id starting with `claude-sonnet-5`): faster, about 5 s per photo instead of 8-17 s; rollback `IMAGE_EFFORT=off`. Every model call of both analyses logs one numbers-only line: `[analyze] image model=<id> in=<input tokens> out=<output tokens> ms=<duration> stop=<stop_reason>` (`[analyze-text] text ...` for text; `in=? out=?` when the reply has no usage, `stop=error` when the call failed). It never holds reply text, names or identifiers; sum `in`/`out` per model to measure the real spend. The text analysis defaults to Haiku 4.5; to try Haiku 5.5 set `TEXT_MODEL=claude-haiku-5-5` (rollback: delete the variable) and compare first with `node scripts/eval-text.js` (see "Text analysis evaluation").

### Nutrition sanity rules

Both analyses pass the model's items through `reconcileItems` (`src/lib/nutrition.js`, pure, never throws, never drops or reorders items) after the item names are cleaned and before the totals are summed, so the response is built from the checked numbers (its shape is unchanged). Five rules run per item, in this order; the constants are `LIMITS` in that file:

1. `invalid`: a present field that is not a finite number >= 0 becomes 0 (a missing field is silently 0).
2. `weight`: `weight_g` is capped at `MAX_ITEM_WEIGHT_G` = 2000.
3. `macro_weight`: protein + carbs + fat + fiber may exceed `weight_g` by `MACRO_WEIGHT_TOLERANCE` = 2% at most, else the macros are scaled down to the weight.
4. `calories_macros`: with `expected` = 4*protein + 4*carbs + 9*fat and `tol` = max(`CALORIE_TOLERANCE_ABS` 40 kcal, `CALORIE_TOLERANCE_REL` 20% of expected), calories below `expected - tol` or above `expected + max(tol, ALCOHOL_KCAL_PER_G * weight_g)` become `round(expected)`. The upper side is wider because drinks carry calories no macro field holds: `ALCOHOL_KCAL_PER_G` = 2.4 kcal per gram of weight is spirits at about 35-40 % ABV, the physical ceiling for a drink, so wine and beer keep their calories (with weight 0 the allowance is 0). Skipped when protein, carbs and fat are all 0.
5. `kcal_density`: calories are capped at `MAX_KCAL_PER_G` = 9 per gram of weight.

When any item changed, one numbers-only line is logged (`console.info`): `[analyze] sanity adjusted=<items changed> calories_delta=<total calories after minus before> rules=<id>:<count>,<id>:<count>` (`[analyze-text]` for text; rule ids sorted; counts are items per rule). Nothing is logged for a consistent reply, and never any meal text, name or identifier.

### Portion estimation (image)

Step 3 of `IMAGE_SYSTEM_PROMPT` is `SCALE_METHOD` (`src/lib/prompts.js`), a scale-grounded method with no per-dish rules and no food dictionary: (1) find objects of roughly standard size in the photo and compare against them (fork about 19-20 cm, table knife about 22 cm, tablespoon about 18-19 cm, teaspoon about 14 cm, cup or mug about 7-8 cm wide, 330 ml can about 6.6 cm wide, credit card 8.6 cm, adult hand about 8-9 cm wide); a plate is not always 26 cm (home plates are usually 20-28 cm, bowls and dessert plates smaller), so derive the plate or bowl diameter from those objects, and only with nothing to compare against assume a home plate of about 24 cm; write the reference objects and the plate diameter in `scale_reference` (short English phrase); (2) estimate each item's `weight_g` from its size against that scale (area and thickness or height) and the usual density of the kind of food, not from a portion size assumed in advance, without inflating (a normal home plate usually holds one normal portion). The restaurant line applies only when the serving clearly looks like a restaurant, and then adds the hidden oil/butter only. The anchors are unchanged. The image reply template is `{ visual_description, scale_reference, draft_name, dish_name, items }` with the same item template as the text reply (no volume field). `scale_reference` is **model-only**, like `visual_description`: never returned, stored or logged; a reply without it is accepted (for example after an `IMAGE_MODEL` rollback to Haiku). The prompt is the evaluated variant `scripts/eval/prompts/portionV2.js` (owner decision 2026-10-03, after three real runs): a test asserts that the runtime strings equal that file's and pins the file by SHA-256, so a prompt change updates both on purpose. An earlier volume method (a `volume_ml` per item and a density rule in `nutrition.js`) raised calories by about 19% and tripled the output in the real run; it was removed and is not shipped.

### Dates and time (wall-clock model)

- A meal's `logged_at` is the **user's wall-clock time**, not an instant: the browser builds it from its own local date and clock (`todayStr()` and `nowTimeStr()` in `public/js/dates.js`) and the server stores it as sent. `food_logs.logged_at` is a `TIMESTAMPTZ`, so every database session is **pinned to UTC** (`src/db/pool.js`); the stored value and the `YYYY-MM-DDTHH:mm` text read back from it are then the same wall clock, whatever zone the database or the server runs in. The server has no zone of its own and never converts.
- "Today" is the browser's local date. `GET /api/streak` and `GET /api/stats/weekly` take `?today=YYYY-MM-DD` (the frontend always sends it); when it is absent the server falls back to the **UTC** date. The streak and the weekly window count back from that date with plain calendar arithmetic (`addDaysUtc` in `src/lib/dates.js`); the browser does the same with `addDays` / `daysBetween` (via `Date.UTC`, so no zone is involved). There is no Israel (or any other) time-zone conversion anywhere.
- The `day` fields of the stats responses are plain `YYYY-MM-DD` strings (never timestamps), safe to compare with `todayStr()`.
- New browser code must use the helpers in `public/js/dates.js` and must not build date or time strings by hand (`toISOString`, `toTimeString`, `toLocaleString` with a `timeZone`).

### Auth and sessions

- The session is an **HttpOnly, SameSite=Strict cookie `fl_session`** (a JWT, 7 days, `Secure` in production), set by `POST /auth/register` and `POST /auth/login`. The response body holds only the username; JavaScript never sees the token. There is **no `Authorization` header** and no token in `localStorage`.
- The JWT carries `{ id, tv }`. `tv` must equal `users.token_version`, so a revocation is one `UPDATE`: `POST /auth/change-password` and `POST /auth/logout-all` bump `token_version` (every other session dies on its next request); `POST /auth/logout` only clears this device's cookie.
- `GET /auth/me` returns `{ username }` and is how the frontend learns at load time whether it is signed in.
- No cookie: `401 UNAUTHORIZED`. A bad, expired, revoked or orphaned cookie: `401 SESSION_EXPIRED` and the cookie is cleared. A database failure is `500 INTERNAL`, never a 401.
- Login is limited per IP (`/auth/login`, `/auth/register`: 10 per minute) and per username (10 failures per 15 minutes; in memory, so it resets on restart and assumes one instance). Trade-off: anyone who knows a username can lock that account out for up to 15 minutes, which is accepted for a single-user app.
- `POST /auth/change-password` is a bcrypt path behind the session cookie, so it is limited per IP (10 per minute, `limits.changePasswordPerMin`) and per user id (10 wrong current passwords per 15 minutes, `limits.changePasswordFailures`; checked before bcrypt, reset on success; same in-memory caveats).

### CSRF

Every state-changing request (any method except GET, HEAD and OPTIONS) must carry `Origin` equal to the normalised `ORIGIN` (the `Referer` origin is accepted only when `Origin` is absent) **and** the header `X-FL-Client: 1`; otherwise `403 CSRF`, before body parsing or auth. `public/js/api.js` adds the header to every call. When testing with curl or supertest, send both. `loadConfig` is the guard that `ORIGIN` is an exact http(s) origin; `createCsrf` itself only throws when the normalised expected origin is `'null'`.

### Error-code contract

Errors are `{ "error": { "code": "..." } }` (plus `fields: { field: code }` for `VALIDATION`). The server sends **no human-language text**: `public/js/errors.js` maps each code to a Hebrew message (`messageFor(err)`). Adding a new code means adding its Hebrew string there.

### Security headers

A strict CSP on every response (`script-src 'self'`: no inline scripts, no inline event handlers, no eval; `style-src` allows inline `style=` attributes), plus HSTS in production and the other Helmet defaults (see `src/middleware/security.js`). Nothing is loaded from third-party origins: the fonts are served from `public/fonts/`. The frontend never assigns `innerHTML` directly; it builds markup with the escape-by-default `html` tag and `setHtml` in `public/js/dom.js`, and uses `data-action` / `data-change` attributes with delegated listeners (`events.js`) instead of inline handlers.

### Frontend modules (`public/js/`)

Plain ES modules, no build step, entry point `main.js` (registers screens, wires event delegation, boots the session). `api.js` (fetch wrapper, `ApiError`), `errors.js` (code to Hebrew), `session.js` (boot, login state, logout), `router.js` (`navigate`, screen hooks), `state.js`, `dom.js` (`html`, `raw`, `setHtml`, modals), `events.js` (delegation), `dates.js`, `format.js` (`formatNumber`, `formatKg`, `MEAL_LABELS`), `profile.js`, `charts.js` (the stats headline, macro bars, hand-drawn bar chart and the weight line graph), `effects.js`, `pet.js` (the capybara: `cloneCapybara`, `decorateCapybara`, `getPetState`, `mountWalkingCapybara`), `streakDays.js` (`daysStripSvg`, the streak as a strip of seven hand-drawn circles for the last seven days, today at the right; the dashboard derives the filled days from `GET /api/streak` and today's meals, no extra call), `receipt.js` (`receiptHtml`, a pure function of the analysis reply), `photos.js` (`photoSrc`, `makeThumbnail`, `uploadThumbnail`, `installPhotoFallback`), `placeholder.js` (`plateSvg`, the drawn plate for a meal without a photo), and `screens/` with one module per screen (`welcome`, `auth`, `dashboard`, `home` (the diary and the edit-meal slip), `camera` (add meal), `analysis` and `analysisView` (waiting, receipt, error), `stats`, `weight`, `settings` (and the two settings slips)). The only `localStorage` use is the cached `fl_profile` (plus removal of the legacy `fl_token` / `fl_username` keys).

### The diary design (`public/css/`, `public/fonts/`)

The look is a personal paper diary: a dark **leather** cover (`--leather` `#22140c`, grain from a tiled SVG `feTurbulence` data-URI, a dashed gold stitch) around cream **ruled pages** (`--page` `#f5ecd9`, `--ink`, `--graphite`, red pen `--red` `#b3311d`, gold foil `--gold`; all tokens in `tokens.css`, no other colour system: the old dark theme and its alias variables are gone). Components (`base.css`, `components.css`): `.phone-frame`, `.page` (the sheet; never scrolls) with `.margin` (the red line) and `.content` (scrolls and draws the 30 px rules itself, so every block is a multiple of 30 px high), `.polaroid` + `.tape`, `.circ` (red-pen circle), `.stamp`, `.penbtn` (red ink button), `.chip`, `.field` (handwritten underline field), `.bubble`, `.ribbon`, `.dock` (the six-button bottom navigation: home, diary, add, stats, weight, settings; the add button is an orange pill) and the receipt (`.receipt-slip` inside `.receipt-lift`, Cousine, serrated edge, printed with `clip-path`). Per-screen rules are in `screens.css`. Motion honours `prefers-reduced-motion` (one rule in `base.css` collapses every animation and transition; a new animation needs no extra rule, a JS-driven one must check it). The hook contract the tests rely on (screen ids `#screen-*`, nav ids `#nav-*`, the field and button ids, buttons found by their Hebrew names) is listed in the plan `docs/superpowers/plans/2026-10-03-ui-redesign.md`; changing an id or a button name means updating the tests in the same commit.

**Fonts** (all self-hosted woff2 subsets, SIL OFL, licences next to them as `OFL-*.txt`; `font-src 'self'`; at most 300 KB in total, asserted by `test/api/frontend-fonts.test.js`, which also fails on any other family, an unreferenced file or a mention of a removed family): **Gveret Levin** for all handwriting, **Suez One** for the wordmark and stamps, **Cousine** for the receipt only (Hebrew and numbers), **Playpen Sans Hebrew** as the Latin / fallback face. **Digit rule:** every digit outside the receipt is drawn in the family `Digits`, which is the Playpen files declared a second time with `unicode-range` U+0030-0039, comma, dot, colon and slash and is the first entry of `--font-text` / `--font-display`, so it applies by itself wherever the stack is used; form controls inherit it (`font-family: inherit`). New markup must not set another `font-family` on a text with numbers. `test/e2e/fonts.spec.js` walks every screen with data, all three stats views and every modal and fails on any digit (a text node or a typed value) not drawn in `Digits`. Gveret Levin has only the regular weight: do not use `font-weight` above 400 or `font-style: italic` on it (the browser would fake them); the receipt's `b` uses the real Cousine 700.

**The capybara** is the original SVG (`<template id="capy-tpl">` in `index.html`) with a light drawn treatment added at runtime by `decorateCapybara` (soft outline, wobble filter `#capyink`, shading, fur ticks, loaf legs); states `ecstatic|happy|neutral|sad|sleeping|surprised|thinking` come from `getPetState`. On the sign-in and stats pages she **walks along the page** (on stats only on a phone taller than 800 px; on a shorter one the walker strip goes, so the three stats views never scroll; the weight page has a small static happy capybara at its top left whose bubble cheers the user on with one of eight fixed messages chosen by the number of entries, and the settings page has none): `mountWalkingCapybara(pageEl, { state, size, bottom })` appends a `.walker` lane, measures her visible body so she turns exactly when she touches the page edge or the red margin line, re-measures through a `ResizeObserver`, and returns `{ stop }`; **a screen must call `stop()` in its leave hook** (the screens keep it in `_walker`). `test/e2e/walker.spec.js` measures her bounds. The welcome cover shows her in her salad bowl; the old logo videos (`salad-logo`, `fire-loop`) are no longer used by the app and were removed from `public/`.

### Hebrew copy and AI naming

**The guard (`src/lib/hebrewName.js`).** Every AI-produced food name (the image `dish_name` and the shown name of a text analysis) goes through `ensureHebrewDishName(anthropic, name, { mode, model })` (`model` is the repair model, `config.textModel` in production, default `MODEL`), which never throws on a bad name. It returns `{ name, action }` with `action` one of `ok`, `repaired`, `cleaned`, `fallback`.
- Mode `dish` (image `dish_name`, strict): anything outside Hebrew letters, nikud, digits, plain ASCII whitespace and `- – — ' " ’ “ ” ( ) , . / + & % : ;` is foreign script (Latin, CJK, Arabic, Cyrillic, emoji, control and invisible characters). At most eight words and 70 characters (the prompt asks for about five; a longer name is cut at a word boundary and a dangling connector is trimmed).
- Mode `userText` (text analysis): the text is shown as typed. Only letters of a non-Hebrew script and unsafe invisible characters count as foreign; emoji, punctuation, symbols and digits stay; no word limit, but at most 200 characters (`maxChars`, set by `analyzeText`); the repair is a translation that must keep every other word.
- A repair reply with `stop_reason` `max_tokens` (cut) or `refusal` counts as a failed repair (the careful cleaning below takes over), so a partial name is never shown.
- Order: if the name is foreign, one small repair call to the AI (Hebrew letters only, the everyday Israeli name) -> if that fails or is still foreign, careful cleaning (a foreign character is removed together with the whole word it touches; stray punctuation and dangling connectors are trimmed) -> if nothing valid is left, the neutral default `מנה`. A clean name that is only too long is shortened, never replaced.
- Logging: one `console.warn` line per non-ok outcome, `hebrewName <repaired|cleaned|fallback>: "<name cut to 80 chars>"`. Nothing else about the user's meal is logged.
- **No per-food hard-coding.** A wrong name is fixed by a general rule (the prompt principles or the guard), never by a list of foods. A per-food exception needs the owner's approval and a reason why no general rule covers it, and is recorded in `docs/hebrew-naming-exceptions.md` (the list is empty).

**Prompt principles (`src/lib/prompts.js`, image analysis; `analysis.js` re-exports the prompts).** The model recognises first, then names: the reply starts with `visual_description` (a short neutral English description, a recognition step for the model only), then `draft_name` (a first attempt at the name), then `dish_name` (the final name, written after re-reading the draft against the rules), then `items`. `visual_description` and `draft_name` are never read, returned, stored or logged; a parse failure logs only its kind, the reply length, the block types and `stop_reason`. The name follows general rules (the everyday name an average Israeli would say, only common words in standard spelling, never an invented word or a transliterated foreign dish name, a simple description by main component and preparation when the everyday word is unknown, a correct general name over a specific wrong guess, Hebrew letters only); the examples in the prompt are illustrations of a rule, never a lookup table. The image prompt carries no per-food recognition hints (step 1 of the method is a general sentence about using the whole plate as context); the portion anchors ("עוגני כמויות") are nutrition quantities, not recognition hints, and stay (sub-project 3 may revisit them). Text analysis keeps the user's own words. The frozen old prompt lives in `scripts/eval/imagePromptV1.js` for the evaluation only and a hash test guards it from edits; `src/` must never `require` anything under `scripts/`.

**Naming evaluation (a developer tool, not part of the app).** It runs the same photos through the old pipeline (old prompt + silent name stripping) and the new one (new prompt + guard), several runs each.

```bash
cd food-logger
node scripts/eval-naming.js              # dry run: prints the photo and call counts and an estimated cost, calls nothing
node scripts/eval-naming.js --yes        # really calls the API (ANTHROPIC_API_KEY from .env); options: --dir eval/photos --runs 3
node scripts/eval-naming.js --also-model claude-sonnet-5-5 --yes   # adds a third column: the new pipeline on that model
node scripts/eval-naming.js --also-model claude-sonnet-5-5 --only-extra --yes   # only the extra column, merged into the existing eval/results.json
node scripts/eval-naming.js --also-model claude-sonnet-5-5 --only-extra --prompt portionV2 --effort low --yes   # the extra variant with a named prompt file and an effort
```

- `--also-model <id>` adds a third variant (the new prompt and guard on another model). It is sent **without the `temperature` parameter** (`analyzeImage(..., { temperature: null })`), because some newer models reject it (`400 temperature is deprecated for this model`); the old/new variants keep their temperature. A Sonnet 5 extra model also gets the low-latency fields of `requestOptionsFor` (default effort low). The "new" variant calls `analyzeImage` without a model, so it runs on Haiku (`MODEL`), not on the production `IMAGE_MODEL`. The guard's repair calls go to `MODEL` (Haiku 4.5; this tool does not use `TEXT_MODEL`).
- `--only-extra` (needs `--also-model`) runs only that variant, e.g. after a failed or changed extra run: it reads the existing `eval/results.json` (which must cover the same photo file names and the same `--runs`, otherwise it refuses), keeps the stored old and new results untouched, replaces the extra results and regenerates `eval/report.html`. Its dry run shows only the extra variant's call count and cost.
- `--prompt <name>` runs the `--also-model` variant with the image prompt of the variant file `scripts/eval/prompts/<name>.js` (for example `prePortion`, the runtime prompt before the portion method, or `portionV2`, the scale-grounded prompt that is now the runtime prompt); an unknown name is an error.
- `--effort <low|medium|high|off>` sets the effort of the `--also-model` variant's request (`off` sends no thinking or effort fields); it only has an effect on Sonnet 5 models (and, as `output_config.effort` alone, on Haiku 5 and later), and the default is low.

- Photos go in `food-logger/eval/photos/` (the whole `eval/` directory is git-ignored; the photos are sent only to the Anthropic API). Output: `eval/results.json` and the report `eval/report.html`.
- Optional `eval/ratings.json`: `{ "<file name>": { "natural": true|false, "note": "" } }`; the report then shows the share of natural names.
- The tool goes through `analyzeImage`, so evaluation runs also use the parse retry: a failing photo costs two calls, the dry-run estimate ignores retries, and the retry can hide the intermittent failure rate being measured (the usage lines below show each call).
- **Every real run costs money and needs the owner's approval.** The tests never call the API.

**Text analysis evaluation (a developer tool, not part of the app; `src/` never requires it).** `scripts/eval-text.js` runs a built-in list of 22 realistic Hebrew free-text meal descriptions (`scripts/eval/textInputs.js`: simple foods, drinks, restaurant dishes, quantities in grams, cups and pieces, mixed items, one deliberately vague, one transliterated, one with emoji, one with Latin letters) through the real `analyzeText` pipeline (the family request rules, the parse retry, the sanity rules and the name guard, exactly as in production) on two or more models and compares them.

```bash
cd food-logger
node scripts/eval-text.js            # dry run: prints the number of calls and an estimated cost; builds no client, calls nothing
node scripts/eval-text.js --yes      # really calls the API (ANTHROPIC_API_KEY from .env, never printed); options: --models claude-haiku-4-5-20251001,claude-haiku-5-5 --runs 1
```

- `--models a,b` (default `claude-haiku-4-5-20251001,claude-haiku-5-5`; 1 to 4 different ids), `--runs N` (1 to 10, default 1), `--yes`. Without `--yes` it is a dry run and reads no secret.
- Output: `eval/text-results.json` and the RTL Hebrew report `eval/text-report.html` (the `eval/` directory is git-ignored): per text and model the name, calories, macros, item list, latency (ms, the whole run), input/output tokens (summed over the retry and repair calls), the guard's outcome (`ok|repaired|cleaned|fallback`, read from its log line), the number of calls and any error; plus a summary per model.
- The estimate is rough: 1,800 input and 600 output tokens per call at per-model rates (Haiku 4.5 $1 / $5 per million tokens; Haiku 5.5 $0.10 / $0.50 with about 30% more tokens; any other id at the Haiku 4.5 rates), repair calls counted like main calls, a parse retry not counted. **Every real run costs money and needs the owner's approval.** The tests never call the API (`test/api/eval-text.test.js` asserts a dry run never constructs a client).

**Hebrew copy workflow (everything the user reads).**
- `node scripts/extract-hebrew-text.js` (from `food-logger/`) collects every Hebrew string into `docs/hebrew-copy-audit.md` and fails if a line with Hebrew is unaccounted for. Run it after changing any user-facing text; the committed table must equal its output (the extractor test checks this part of it).
- Proposals live in `docs/hebrew-copy-proposals.json`, keyed by the exact current text (`{ proposed, reason, level: recommended|optional, decision }`). Workflow: add a proposal -> the owner approves (`decision`) -> change the app text **and delete the entry from the JSON in the same commit** (a leftover entry is stale and fails the extractor test). The file is currently `{}`. A readable summary is in `docs/hebrew-copy-audit-summary.md`.
- `test/api/hebrew-spelling.test.js` fails if a known wrong form returns; add a wrong form that must not come back there.
- `test/e2e/hebrew-baseline.spec.js` compares all visible Hebrew text, per screen, with `test/e2e/__snapshots__/he-text.json` (the collector skips the capybara's own SVG `<text>` glyphs, her "z z z" and "?", which are drawing, not copy; chart labels are copy and are kept).
